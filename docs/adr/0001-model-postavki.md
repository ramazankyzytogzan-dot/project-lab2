# ADR-001: Выбор модели поставки и рабочей методологии для проекта CafeFlow

* **Статус:** Принято (Accepted)
* **Дата:** 16 сентября 2026 г.
* **Авторы:** Қуанышбаева Айкүн, Рамазанқызы Тоғжан
* **Проект:** CafeFlow (Автоматизация работы небольшого кафе)

## 1. Контекст и постановка проблемы (Context)
Проект CafeFlow разрабатывается командной парой из 2 человек (Backend + Frontend) в рамках учебного семестра (12 недель). 
Заказчику (Управляющему кафе) требуется рабочий модуль приема заказов и интерактивной карты столов к 6-й неделе семестра. Необходимо выбрать модель поставки и рабочую методологию, которые обеспечат параллельную разработку фронтенда и бэкенда по строго согласованным API-контрактам, исключая риски срыва сроков.

## 2. Движущие силы (Driving Factors)
* Жесткий дедлайн учебного семестра (12 недель).
* Командное распределение ролей: 1 Backend / PM (Айкүн) + 1 Frontend / UI (Тоғжан).
* Необходимость демонстрации работающего MVP (карта столов + выбор блюд) к 6-й неделе.
* Высокие риски рассинхронизации API между фронтендом и бэкендом при независимой разработке.

## 3. Рассмотренные варианты (Considered Options)
1. **Вариант 1: Pure Waterfall (Чистый каскад)** — Написание полного ТЗ, разработка всех модулей по очереди и интеграция только на 12-й неделе.
2. **Вариант 2: Pure Scrum (Чистый Скрам)** — Работа по 2-недельным спринтам с проведением всех формальных Scrum-ритуалов (Daily Standup, Refinement, Retrospective).
3. **Вариант 3: Гибридная модель (Discovery Phase + Scrumban)** — 1-недельная Discovery-фаза (OpenAPI/Swagger, ERD, Figma-макеты), с последующей поставкой по Kanban (с фиксацией WIP-лимитов) и проведением регулярных совместных интеграционных тестов.

## 4. Решение (Decision Outcome)
**Принят Вариант 3: Гибридная модель (Discovery Phase + Scrumban).**

### Обоснование выбора:
* **Discovery-фаза (Недели 1–2):** Фиксирует OpenAPI-спецификацию и UI-макеты в Figma до написания кода. Напарница сразу разрабатывает интерфейсы на мок-данных, пока строится БД и API.
* **Delivery-фаза (Scrumban, Недели 3–11):** Разработка управляется через визуализацию потока задач в GitHub Projects с ограничением WIP (Work In Progress) = 2 задачи на каждого исполнителя.

## 5. Причины отказа от других вариантов (Rejection Reasons)
* **Отказ от Варианта 1 (Waterfall):** Высокий риск обнаружения интеграционных сбоев при объединении фронтенда и бэкенда в самом конце проекта.
* **Отказ от Варианта 2 (Pure Scrum):** Избыточные временные затраты на проведение формальных ежедневных митингов и оценивание задач в Story Points в компактной команде из 2 человек.

## 6. Последствия решения (Consequences)

### Положительные последствия (+):
* Параллельная независимая разработка фронтенда и бэкенда со 2–3 недели.
* Показ работающего MVP управляющему кафе точно на 6-й неделе.
* Четкая прозрачность распределения ответственности на доске GitHub Projects.

### Отрицательные последствия и риски (-):
* Любые изменения в эндпоинтах API требуют немедленного обновления OpenAPI-схемы и повторного согласования между разработчиками.

## 7. Критерий пересмотра (Re-evaluation Trigger)
Если к 6-й неделе модуль создания заказа не удастся успешно протестировать на связке Frontend + Backend, скоуп проекта будет пересмотрена с заморозкой модуля отчетов и сокращением до управления столами и меню.
