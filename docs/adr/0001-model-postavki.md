# ADR-001: Выбор модели поставки и ветвления в Git для проекта CafeFlow

* **Статус:** Принято (Accepted)
* **Дата:** 2026-09-16
* **Авторы:** Команда разработки CafeFlow

---

## 1. Контекст (Context)
Для обеспечения предсказуемого процесса разработки, высокой стабильности системы **CafeFlow** и координации работы команды необходимо зафиксировать единую модель поставки программного обеспечения (Release & Branching Model) и правила управления исходным кодом в Git-репозитории.

## 2. Движущие силы (Drivers)
* **Необходимость частых и безопасных релизов:** Проект требует регулярного добавления функционала без нарушения работы основного сервиса.
* **Минимизация конфликтов слияния (Merge Conflicts):** Команда должна избегать длительно живущих веток, приводящих к сложностям при интеграции.
* **Прозрачность процессов:** Четкая привязка веток, коммитов и Pull Request'ов к задачам в GitHub Projects / Issues.
* **Простота поддержки:** Минимизация накладных расходов на сопровождение сложных схем ветвления для малых и средних команд.

## 3. Рассмотренные варианты (Considered Options)
1. **Trunk-Based Development (TBD)** — разработка с единой основной веткой (main), куда напрямую или через короткоживущие ветки сливаются небольшие изменения.
2. **GitFlow** — классическая модель с долгоживущими ветками main, develop, eature/*, elease/* и hotfix/*.
3. **GitHub Flow** — упрощенная модель на базе main и короткоживущих тематических веток (eature, ix), сливаемых через Pull Request.

## 4. Решение (Decision)
Принять **GitHub Flow** (с элементами Trunk-Based Development) в качестве основной модели поставки и управления ветками.

### Правила реализации:
* Основной защищенной веткой является main. Прямой push в main запрещен (только через Pull Request).
* Для каждой задачи создается отдельная короткоживущая ветка от main.
* **Правило жизни веток:** "Одна ветка — одна задача, живёт не дольше 3 дней".
* Все ветки создаются по соглашению именования: eat/ABC-12-short-name, ix/ABC-12-short-name, 	ech/ABC-12-short-name, docs/ABC-12-short-name.
* Все коммиты должны соответствовать стандарту Conventional Commits (eat:, ix:, docs:, 	ech:).

## 5. Последствия (Consequences)

### Положительные (Positive)
* **Быстрый цикл обратной связи:** Изменения быстро попадают в main и готовы к развертыванию.
* **Упрощение работы с Git:** Отсутствие необходимости поддерживать синхронизацию между main и develop.
* **Снижение риска рисков интеграции:** Короткие ветки сводят к минимуму сложные конфликты слияния.
* **Прозрачное проведение код-ревью:** Каждый Pull Request наглядно отражает изменения по конкретной задача из Kanban-доски.

### Отрицательные (Negative)
* Требуется высокая дисциплина команды по атомарности задач (задача должна укладываться в 1-3 дня).
* Требуется наличие автоматических тестов (CI/CD) для предотвращения попадания багов в ветку main.

## 6. Критерии пересмотра (Re-evaluation Criteria)
Настоящее решение может быть пересмотрено при появлении следующих факторов:
* Увеличение состава команды разработки до 15+ человек, работающих одновременно над независимыми релизами.
* Переход на жесткий календарный цикл версионирования с необходимостью поддержки нескольких одновременных релизных версий (Long Term Support / LTS).
* Увеличение длительности разработки крупных эпиков до более чем 1-2 недель без возможности их разбиения на feature flags.
